# 화자 구분 (화자분리가 안 될 때)

> 다루는 것: Whisper가 화자를 나누지 못한다는 가정에서 면접관(질문)과 지원자(답변)를 구분하는 방법, 방법별 비교, 측정 결과, 트랙별 권장, 현업에 확인할 것.
>
> 상태: ①③④는 합성 대화로 측정했다. ⑤(LLM)는 사내 LLM이 없어 **측정하지 못했다.** ②(채널)는 자리만 있다. 실제 면접 녹음으로는 아무것도 재지 못했다.

## 1. 문제

- 방 마이크 하나로 받은 음성에는 면접관 여러 명과 지원자 한 명의 말이 섞여 있다. Whisper는 글만 주고 누가 말했는지는 주지 않는다(고 가정한다).
- 필요한 구분은 두 가지뿐이다: `INTERVIEWER` / `CANDIDATE`. 면접관이 여러 명이어도 서로 나눌 필요는 없다.
- 틀리면 생기는 일: 면접관의 말이 지원자 답으로 평가 근거에 들어간다(평가 그래프는 면접관이 아닌 발화만 근거로 쓴다), 질문 매칭이 빠진다, 꼬리질문이 엉뚱한 때 나온다.

## 2. 구현: 판정기 체인

발화마다 판정기를 순서대로 돌려 **처음 답을 낸 판정기**의 결과를 쓴다(`app/speaker/chain.py`). 순서는 `SPEAKER_CHAIN`으로 바꾼다. 아무도 답하지 못하면 `UNKNOWN`.

| 순서 | 판정기 | 근거 | `speakerMethod` | 상태 |
| --- | --- | --- | --- | --- |
| ① | `manual` | 면접관이 화면에서 지정한 역할(`role` 메시지). `AUTO`면 넘어간다 | `MANUAL` | 구현 |
| ② | `channel` | 마이크·트랙이 사람별로 나뉘어 올 때 채널 | `CHANNEL` | 자리만(항상 넘어간다) |
| ③ | `question_match` | 준비된 질문·질문 은행·방금 제안한 꼬리질문과 유사도 0.55 이상이면 면접관 | `QUESTION_MATCH` | 구현 |
| ④ | `rule` | 의문형·요청형 어미, 상대 높임, 1인칭, 평서형 어미, 길이, 직전 화자, 마무리 문답 구간 | `RULE` | 구현 |
| ⑤ | `llm` | 최근 대화 6개와 함께 LLM에 묻는다. 확신 0.6 미만이면 `UNKNOWN` | `LLM` | 구현(실제 모델로 미측정) |

- 사람이 나중에 고치는 길도 있다: `utterance.fix` 메시지 → `MANUAL`로 바뀌고 `transcript.updated`가 나간다.
- 사후 STT 때 같은 체인으로 다시 판정한다. 사람이 고친 화자는 보정 전사에 물려준다.

| ⑤ LLM 문맥 판정 | `llm.fast` 호출 1회(①~④가 못 정한 발화만) | 예(+LLM 시간) | 미측정 | 비용·지연. 모델 품질에 달림 |

## 4. 측정

### 방법

- 자료: `tests/fixtures/speaker_dialogue.json`. `scripts/gen_speaker_fixture.py`로 만든 **합성 면접 대화 125발화**(면접관 61, 지원자 64)와 질문 은행 100개. 음성 인식 결과처럼 문장 부호가 없다.
- 발화 종류: 질문 은행 문장 그대로(20), 바꿔 말한 질문(13), 즉석 질문(13), 진행 말(10), 지원자 답(52), 짧은 답(4), 질문을 되받아 시작하는 답(3), 지원자의 되물음(5), 그에 대한 면접관의 설명(5).
- 실행: `python scripts/eval_speaker.py`. 직전 화자 문맥에는 정답이 아니라 **판정 결과**를 넣는다(한 번 틀리면 다음에 영향을 준다).
- fake LLM이므로 ⑤는 빼고 ①~④만 쟀다(스크립트가 이를 출력에 밝힌다).
- ①은 사람이 하는 일이라 가정으로 흉내 냈다: 화자가 바뀔 때 전환을 잊을 확률 0% / 10%.

### 읽는 법 (중요)

- **이 숫자는 낙관적이다.** 규칙(④)의 낱말·가중치를 이 합성 대화를 보면서 맞췄다(맞추기 전 첫 측정은 정확도 82.4%, 면접관 재현 70.5%였다). 같은 자료로 맞추고 같은 자료로 잰 값이다. 대화도 규칙을 만든 쪽이 썼다. 실제 면접에서는 더 낮다고 봐야 한다.
- 합성 대화는 문장이 끝까지 말해지고, 끼어들기·말 겹침·말끝 흐리기·잘못 인식된 글자가 없다. 실제 전사에서는 어미가 틀리게 인식되면 규칙이 바로 흔들린다.
- **질문 은행의 크기는 자동 체인의 정확도를 바꾸지 못했다**(0·20·100개 모두 95.2%). 은행 문장 그대로인 질문은 의문형이라 규칙만으로도 잡히기 때문이다. 은행이 커지면 달라지는 것은 ③이 근거가 되는 비율(면접관 발화의 0% → 11.5% → 32.8%)과 `question.matched`로 연결되는 질문 수다.
- **문자 n-gram 유사도는 바꿔 말한 질문을 찾지 못한다.** 그대로 말한 질문(0.74 이상)과 지원자 답(0.30 이하)은 잘 갈리지만, 바꿔 말한 질문(0.16~0.36)은 답과 겹친다. 임계값을 낮춰서는 해결되지 않는다. 바꿔 말한 질문까지 매칭하려면 임베딩(`EmbeddingProvider`)이 필요하다.
- ③으로 판정한 것은 모두 맞았다(지원자 답을 질문으로 잘못 본 경우 0건). 근거로서 믿을 만하다.
- 남은 오류는 본질적으로 어려운 것들이다: "네 알겠습니다", "네 답변 감사합니다"(누구나 하는 말), "조금만 더 구체적으로요"(어미 없는 조각), 지원자의 "다시 말씀해 주시겠어요". 이런 것은 ⑤(LLM)나 사람이 정해야 한다.
- 전환을 10% 잊는 사람(① 90.4%)보다 자동 체인(95.2%)이 높게 나왔지만, 위 낙관을 감안하면 "자동이 사람보다 낫다"는 결론은 낼 수 없다.

## 5. 권장

### 신입 (대면, 방 마이크 하나)

1. 기본은 **자동 체인**(`SPEAKER_CHAIN=manual,channel,question_match,rule,llm`, 역할은 `AUTO`).
2. 화면에서 틀린 발화를 **한 번 눌러 고치는 기능**(`utterance.fix`)을 눈에 띄게 둔다. `UNKNOWN`은 다르게 표시한다.
3. 역할 전환 버튼(①)은 선택 기능으로 둔다. 면접관이 조작에 신경 쓰게 만드는 것이 부담이라 기본으로 요구하지 않는다.
4. 평가·보고서는 화자가 틀릴 수 있다는 전제로 "참고"로만 쓴다. 근거 발화 번호를 같이 보여 사람이 확인할 수 있게 한다.
5. 장비를 둘 수 있으면 **마이크 2개**(지원자 앞 지향성 + 면접관 쪽)가 가장 확실하다. 그 경우 프론트가 채널을 나눠 보내야 하고(계약 변경), `ChannelJudge`에 잇는다.

### 경력 (화상, Knox Teams)

1. **참가자별 음성 트랙을 받을 수 있는지가 먼저다.** 받을 수 있으면 채널 = 사람이므로 ②로 끝난다(추정이 필요 없다).
2. 받을 수 없고 지금 가정대로 브라우저가 음성을 보낸다면: 면접관 PC에서 "내 마이크"(면접관)와 "화상에서 나오는 소리"(지원자)를 따로 잡아 보내는 방법이 있다. 프론트 변경과 계약 변경(오디오 프레임에 채널 표시)이 필요하다.
3. 둘 다 안 되면 신입과 같은 자동 체인을 쓴다. 화상은 말이 겹치는 일이 적어 대면보다 유리할 것으로 보지만 재지 못했다.
4. 경력 보고서(DETAILED)는 시간이 넉넉하므로 사후 STT의 재판정 결과를 쓰는 `REFINED` 보고서를 기준으로 삼는다.

## 6. 현업에 확인할 것

| 항목 | 왜 |
| --- | --- |
| 면접실 마이크 구성(개수, 위치, 종류) | 채널 분리가 가능한지, VAD 임계값 |
| 면접관이 역할 전환 버튼을 쓸 의향이 있는지 | ①을 기본으로 할지 |
| 면접관이 질문 은행·준비된 질문을 얼마나 그대로 읽는지 | ③이 잡는 비율. 바꿔 말하는 일이 많으면 임베딩이 필요하다 |
| 화자가 틀렸을 때 허용할 수 있는 수준(평가에 쓰는 정도) | UNKNOWN을 늘리고 정확도를 올릴지(임계값) |
| 실제 면접 녹음(동의받은 것) 몇 건으로 측정할 수 있는지 | 위 숫자를 실제 값으로 바꾸려면 필요하다 |
| Knox Teams에서 참가자별 음성·화자 정보를 받을 수 있는지 | 경력 트랙의 방법 결정 |
| DS API Hub의 Whisper가 화자 정보나 단어별 시각을 주는지 | 준다면 ②에 잇거나 말 겹침을 나눌 수 있다 |
| 그룹 면접(지원자 여러 명)이 있는지 | 있으면 두 가지 구분으로는 부족하다 |

## 7. 판정기를 더하거나 바꿀 때

- `app/speaker/base.py`의 `SpeakerJudge`를 구현한다(`judge(ctx) -> SpeakerDecision | None`, 못 정하면 `None`).
- `app/speaker/chain.py`의 `build_speaker_chain` 안 표에 이름을 더하고, `SPEAKER_CHAIN`에 넣는다(기본값은 바꾸지 않고 합친다).
- 규칙을 고쳤으면 `python scripts/eval_speaker.py`를 돌려 이 문서의 표를 고친다. `tests/test_speaker_matching.py`에 회귀 방지선(정확도 0.90 이상)이 있다.
- 실제 녹음으로 잴 수 있게 되면 같은 JSON 모양(`utterances: [{speaker, kind, text}]`, `bank: [{id, text}]`)으로 자료를 만들어 `eval_speaker.py`의 `FIXTURE`를 바꿔 돌린다. 실제 전사는 저장소에 넣지 않는다.
